# v0.3.0 BFABEWW 产品与服务认知规则

> 状态：已确认  
> 适用范围：品牌可信底座  
> 当前阶段只形成可信信息和认知洞察，不生成营销内容。

## 1. 模型定位

BFABEWW 只用于分析品牌下的产品或服务，不用于品牌认知分析，也不是要求客户填写的七个并列表单。

Base 是基础信息收集与充分性门槛，不输出洞察结论。Base 通过后，系统才分析 Feature、Advantage、Benefit、Evidence、Weakness、Worth 六个认知维度。

## 2. 品牌事实库结构

```text
品牌事实库
├─ 事实档案
│  └─ 用户填写或确认的品牌与产品实际信息
├─ 认知洞察
│  └─ AI 分析并由用户审核的产品 BFABEWW 结论
└─ 其他
   └─ 为后续知识类型预留的位置
```

规则：

1. 事实档案不受 AI 分析影响；
2. AI 不能依据认知洞察创建、覆盖或改写事实档案；
3. 用户审核修改洞察时，只修改认知洞察；
4. 联网参考不自动写回事实档案；客户明确采用时，仍需通过产品结构化字段提交；
5. 预留分区当前不承载业务规则。

## 3. 信息来源分层

| 信息类型 | 来源 | 在 BFABEWW 中的作用 |
| --- | --- | --- |
| 事实档案 | 客户填写的产品结构化信息及可继承品牌事实 | 产品事实以及可继承品牌事实的来源 |
| 外部参考 | 行业、竞品、媒体、评论及其他公开信息 | 补充背景、比较维度和待确认线索 |
| 模型推断 | 模型基于事实与参考形成的判断 | 只能形成待审核的认知洞察 |

联网信息只作为带来源的分析参考，不能被表述为该产品已经确认的事实，也不能由系统自动写回产品字段。

## 4. Base 充分性门槛

### 4.1 产品或服务 Base

产品必须具备名称、产品或服务类型、能够说明具体提供内容的简介，并在核心特点、优势、应用场景、可解决问题中至少填写一项；否则 Base 判定为信息不足，并停止该产品的其他六个维度分析。

品牌信息是否充分不属于产品 Base 的判断条件；后续单独建立或更新产品认知时，只要产品自身信息充分就可以执行分析。首次认知建立为了统一确认，仍须等待品牌和纳入产品全部通过预检后再启动批次。

### 4.2 Base 不足后的处理

系统不继续生成洞察，而是提供：

1. 需要补充的信息清单；
2. 返回对应产品字段进行手动补充；
3. 补充后重新执行 Base 检查。

## 5. 六个分析维度

### 5.1 Feature

说明产品或服务通过什么具体特征、机制、工艺、技术、功能或服务流程提供价值。

- 必须基于事实档案中的具体信息；
- “专业、高端、领先、优质、创新”等形容词不能单独作为 Feature；
- 缺少具体、可核验特征时输出“信息不足”。

### 5.2 Evidence

说明哪些认证、资质、报告、数据、技术文档或案例可以支持产品事实或产品主张。

- 每项证据必须说明来源、证明对象和适用范围；
- 未经确认的外部参考不能作为正式 Evidence；
- 只有笼统口碑或无法追溯的描述时输出“信息不足”。

### 5.3 Advantage

说明相对于同类产品、替代方案或明确比较维度，该产品为什么值得选择。

```text
Feature + Evidence + 比较参考 → Advantage
```

- 至少有一项自身具体特征；
- 必须存在比较对象或比较维度；
- 客户填写的产品优势属于分析输入和待验证主张，不能不经判断直接作为最终 Advantage；
- 只有自身特点、没有比较依据时，最多形成“部分支持”的潜在优势；
- “行业第一、领先、唯一”等结论没有明确证据时禁止输出。

### 5.4 Benefit

说明特征和优势最终为目标客户带来什么价值。

```text
目标客户 + 特定场景 + 用户问题 + Feature / Advantage → Benefit
```

- 必须能解释从特征到用户利益的因果路径；
- 不能把可能收益写成确定效果；
- 缺少目标客户、场景、问题或价值机制时输出“信息不足”。

### 5.5 Weakness

说明产品或服务不适合什么情况，以及优势在什么条件下不成立。

- 使用事实档案中的限制、适用条件、服务范围、成本或交付取舍；
- 外部评论只能形成待核实线索，不能直接认定产品弱点；
- 没有可用信息时输出“信息不足”，不能输出“没有弱点”。

### 5.6 Worth

说明产品承载什么价值取向，以及希望以怎样的方式为客户创造价值。

- 可以继承与该产品适用的品牌价值观、创立理念和经营原则；
- 也可以依据产品自身明确的设计目标、服务原则或取舍形成；
- 不得根据产品特点反向推导或修改品牌价值观；
- 没有可用事实时输出“信息不足”。

## 6. 品牌事实继承

- 产品可以使用明确适用于它的品牌事实；
- 继承后仍保留品牌事实的来源和原始归属，不复制成新的产品事实；
- 品牌分析不得使用产品事实或产品洞察；
- 产品事实不能上升为品牌事实，也不能反向改变品牌认知；
- 单个产品信息不足不影响品牌分析或其他信息完整的产品。

## 7. 洞察支撑状态

每个分析维度使用以下状态，不使用百分比置信分：

| 状态 | 含义 |
| --- | --- |
| 依据充分 | 事实档案足以支持当前结论 |
| 部分支持 | 有事实基础，但仍包含需要客户判断的推导 |
| 信息不足 | 无法形成可靠结论 |
| 存在冲突 | 不同信息相互矛盾，系统不能自行选择 |

“信息不足”和“存在冲突”都是合法分析结果，不得通过重新措辞或补充模型常识掩盖。

## 8. 洞察输出结构

每个 Feature、Advantage、Benefit、Evidence、Weakness、Worth 结果至少包括：

- 洞察结论；
- 适用范围：具体产品或服务；
- 支撑的事实档案信息；
- 使用的外部参考；
- 推导理由；
- 支撑状态；
- 缺失信息或冲突说明；
- 审核状态。

所有实质性结论必须能够追溯到事实档案或被明确标记为模型推断。

## 9. 用户审核与版本

- 用户可以修改、确认、不采用洞察，或者接受“信息不足”；
- 用户对洞察的修改只写入认知洞察，不影响事实档案；
- 确认后的洞察版本成为当前产品认知基准，不可原地修改；
- 产品信息或其继承的品牌事实变化后，是否点击“更新洞察”由用户决定；
- 用户不更新时继续使用原洞察；
- 新洞察确认前继续使用原版本，确认后才切换；
- 历史版本永久保留，并继续作为历史检测和分析的依据。

首次同时形成品牌与产品洞察时，产品结果与品牌结果进入同一个审核环节，由用户完成修改后一次确认，不要求分别提交。

## 10. 当前非目标

- 不生成营销内容；
- 不要求客户直接管理后台事实库；
- 不分析或生成品牌认知；
- 不让联网信息未经确认进入事实档案；
- 不因认知洞察变化修改事实档案；
- 不强制六个分析维度都有结论。
